# 项目审查与后续改进方向

## 当前项目做对了什么

这个项目最有价值的地方，是没有把“策划配置生成”停留在一次性文本生成，而是围绕游戏研发中的配置交付链路做了闭环：

- 需求输入有结构化输出。
- 配置草案经过 schema、引用和规则校验。
- Reviewer 和 Repairer 分离，避免审查和修改混在一起。
- 最终配置会再次校验。
- 测试场景和 benchmark 让结果可评测。
- badcase 记录真实 LLM 的脏输出和 hardcase，避免静默失败。
- Web Console 展示 trace，能让非作者理解每一步发生了什么。

## 当前不足

### 1. 配置类型还比较窄

当前覆盖 weapon、upgrade、reward、item，并可选涉及 skill。真实项目里的配置会更复杂，例如活动、关卡、掉落池、商店、任务链、技能状态、Buff、条件表达式、运营开关、多语言文本和 AB 实验。

改进方向：优先扩展一个真实业务域，例如“新手成长线配置”或“活动奖励配置”，不要无边界堆很多表。

### 2. Design Reference 仍然偏静态

现在的数值参考更像固定规则和区间。真实策划配置通常依赖历史版本、经济系统、关卡节奏、付费点、玩家分层和运营目标。

改进方向：引入小型历史配置样例和版本差异，做 retrieval-style reference，让 Agent 能比较“当前需求和历史设计的偏离”。

### 3. Repair 策略仍然简单

当前 Repairer 能修复确定性问题，但复杂冲突还不能很好处理，例如“稀有武器必须强，但不能破坏新手期平衡”这类目标冲突。

改进方向：增加 repair policy，例如最小改动原则、优先修引用、再修硬规则、最后修平衡性，并在报告中解释为什么这样修。

### 4. Benchmark 数据集还不够真实

Phase 3 benchmark 有 hardcase，但样本仍是手写小样本。真实业务需要覆盖更多策划表达方式、模糊需求、冲突需求和跨表引用。

改进方向：把 benchmark 分层：正常样本、格式噪声样本、引用缺失样本、规则冲突样本、平衡性争议样本、真实 LLM schema drift 样本。

### 5. 指标还偏工程正确性

当前指标主要衡量 schema、引用、规则、修复成功和测试覆盖。它们重要，但还不能完全代表“配置是否好玩、合理、符合版本目标”。

改进方向：增加更接近游戏业务的指标，例如成长曲线偏离度、经济消耗合理性、奖励价值密度、稀有度一致性、一次性奖励风险和测试覆盖缺口。

### 6. Web Console 还不是生产工具

当前 Web Console 适合演示和排查，但还没有权限、版本管理、多人协作、配置 diff 审批、接入真实配置仓库等生产能力。

改进方向：面试中不要把它说成完整平台，而要说成本地 prototype，用于验证 Agent 工作流、trace 和评测闭环。

## 不建议继续堆的功能

- 不急着做登录、数据库、Docker、复杂部署。
- 不急着接很多 LLM provider。
- 不急着做大而全的前端页面。
- 不急着把所有模块都包装成 Agent。
- 不急着追求 100% repair success rate，因为 badcase 能暴露边界，反而更真实。

## 更值得补强的方向

1. 深化一个业务域：例如新手武器与奖励成长线。
2. 增加历史配置参考：让系统能解释“为什么这个数值合理”。
3. 改进 hardcase taxonomy：把 badcase 分类成 schema、reference、rule、balance、ambiguity。
4. 增加 config diff：展示草案到最终配置具体改了哪些字段。
5. 增加策划可读报告：把技术错误翻译成策划能理解的修改建议。
6. 接入真实 LLM 做少量对比：说明 MockLLM、真实 provider 和 badcase 机制的边界。

## 面试时的诚实表述

可以这样说：

“这个项目不是要证明我做了一个完整商业化工具，而是验证一个游戏研发管线里的 Agent 工作流：LLM 负责生成和判断，确定性工具负责兜底校验，blackboard 负责追踪上下文，benchmark 和 badcase 负责暴露边界。下一步我会优先补真实配置样本和业务指标，而不是继续堆 UI 或 Agent 数量。”
