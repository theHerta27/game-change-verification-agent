不需要把“完整演示”理解成**面试现场从零改 C# 代码**。这既不现实，也不是展示项目能力的最佳方式。

更合理的是：

> **提前准备真实的代码变更和配置变更，面试现场让工具链对这些真实变更执行分析、校验、构建和运行验证。**

## 面试时一定要演示项目吗？

不一定。不同面试官和面试轮次差别很大，岗位描述里也没有写“必须现场演示”。

常见情况更可能是：

1. 让你介绍项目背景和解决的问题。
2. 画架构图，解释各模块。
3. 深挖一个技术难点。
4. 询问为什么使用 Agent、LLM 的边界在哪里。
5. 追问异常处理、测试、评测和实际效果。
6. 有时让你共享屏幕展示项目。
7. 也可能完全不看界面，只讨论代码和设计。

因此你应该做到：

```text
不演示，也能用语言和架构图讲清楚；
需要演示，可以在 5～10 分钟内稳定跑完；
现场运行失败，还有录屏、截图和报告作为备用。
```

重点不是“炫一个界面”，而是让面试官相信：你确实做过、理解它、知道局限，并且能够解释工程设计。

# 代码变更可以提前准备

“开发者提供代码变更”不等于面试现场写代码。

你可以提前在 Git 中准备两个提交：

```text
commit A：原始版本
commit B：增加多资源奖励支持
```

两个提交之间形成真实代码 Diff，例如：

```text
RewardConfig.cs
RewardManager.cs
RuntimeContractLoader.cs
TelemetryRecorder.cs
```

面试现场点击：

```text
审查当前代码变更
```

Code Review Agent 读取 `commit A -> commit B` 的真实 Diff，然后输出：

* 兼容性问题
* 空值风险
* 奖励重复发放风险
* telemetry 遗漏
* 测试建议

这完全是真实演示，不是伪造。只是代码由你提前写好，而不是现场写。

实际代码来源可以诚实标记为：

```text
developer_authored：开发者编写
ai_assisted：开发者借助 Codex 编写
agent_generated_candidate：代码生成 Agent 产生的候选补丁
```

第一版建议使用 `developer_authored` 或 `ai_assisted`。不要为了演示完整而强行再做一个代码生成 Agent。

# 推荐准备两个主演示案例

## 演示一：纯配置变更

这是 Config Agent 的主场景。

初始运行：

```text
Run A
通关时间：30 秒
目标时间：60～90 秒
首通后：能够连续升级两次
```

策划输入：

```text
延长新手试炼到 60～90 秒，并让首通奖励只能支持一次升级。
```

Config Agent 提出：

```text
普通敌人生命值：200 → 260
精英敌人生命值：700 → 900
首通强化石：3 → 1
```

策划点击批准，执行：

```text
静态校验
→ 导出 Unity Contract
→ 自动试玩
→ 采集 telemetry
```

得到：

```text
Run B
通关时间：68 秒
首通后：只能升级一次
```

这个演示不涉及代码修改，但已经能完整说明配置 Agent 的价值。

---

## 演示二：配置契约和代码共同变化

这是两个 Agent 协作的场景。

需求：

```text
首通奖励从只支持金币，升级为支持金币和强化石。
```

配置变化：

```json
"reward_items": [
  {"item_id": "item_gold", "amount": 100},
  {"item_id": "item_refine_stone", "amount": 1}
]
```

代码变化由你提前准备：

```text
Unity C# 数据模型增加 reward_items
奖励结算逻辑遍历多资源
Loader 兼容旧 v1 配置
telemetry 记录多资源奖励
```

Code Review Agent 现场审查这个 Diff，例如发现：

```text
阻断问题：
v1 配置中 reward_items 可能为 null，
RewardManager 直接遍历会触发 NullReferenceException。

建议：
为空时回退到旧 gold_reward，或者初始化为空数组。
```

随后运行已经准备好的修复版本：

```text
单元测试
→ Unity C# 编译
→ Windows Build
→ 自动试玩
→ 奖励验证
```

最后展示统一报告：

```text
配置 Schema：通过
跨表引用：通过
代码审查阻断问题：已修复
C# 编译：通过
Unity 运行：通过
金币与强化石发放：通过
首通经济目标：通过
```

这就足以证明两个 Agent 接入了同一研发流程。

# 不建议现场做什么

不要把主演示设计成：

```text
现场让大模型生成一大段 C#
→ 自动直接覆盖项目
→ 编译 Unity
→ 期待一次成功
```

风险太高：

* 模型接口可能超时；
* 输出可能漂移；
* Unity 编译可能慢；
* 现场网络可能异常；
* 一个小错误就会让整个演示停住。

真正成熟的研发工具也不会允许模型生成代码后无审批直接写入主项目。

更合理的是：

```text
代码生成候选 Patch
→ 显示 Diff
→ 人工批准
→ Code Review
→ 测试和编译
```

但这可以作为后续能力，不是当前必须完成的能力。

# 最稳妥的演示准备方式

建议准备三层保障。

## 第一层：确定性现场演示

使用 Mock 或固定 fixture，保证：

```text
输入确定
输出确定
流程稳定
无需外网
```

Mock 必须明确标记为“工作流回归演示”，不能说它代表真实模型效果。

## 第二层：真实模型案例

提前保存一次真实 DeepSeek 运行记录，包括：

```text
原始输入
模型输出
Provider 和模型名
Schema 结果
约束对齐结果
最终配置
```

现场网络正常时可以再跑一次；网络异常就展示保存的真实运行记录。

## 第三层：完整录屏

准备一个 3～5 分钟视频，完整记录：

```text
选择 Run A
→ 输入修改要求
→ 查看配置 Diff
→ 批准
→ Unity 自动运行
→ 查看 Run B
→ 查看统一报告
```

录屏不是用来取代现场讲解，而是防止环境故障。

# 面试现场最适合的 8 分钟演示结构

### 第 1 分钟：问题背景

> 游戏配置变更经常涉及策划目标、跨表配置、Unity 加载和实际运行效果。我做了一个真实可运行的新手试炼，并将配置变更和代码审查 Agent 接入同一研发验证流程。

### 第 2～4 分钟：配置调优闭环

展示：

```text
Run A 失败
→ Config Diff
→ 人工批准
→ Run B 改善
```

### 第 5～6 分钟：代码审查

展示提前准备的真实 Git Diff，以及 Code Review Agent 发现的一个真实问题。

### 第 7 分钟：统一证据

展示：

```text
配置校验
代码审查
测试
Unity Build
telemetry
Run A / Run B
```

### 第 8 分钟：说明边界

主动说清楚：

* Mock 只用于确定性回归；
* 真实模型不能保证一次生成成功；
* 单次试玩不是统计学 A/B；
* 配置和代码修改都需要人工批准；
* 当前只支持新手试炼垂直切片。

这反而会让项目更可信。

# 你最需要准备的不是现场写代码，而是回答追问

面试官可能会问：

```text
为什么这个需求只改配置，不改代码？
什么时候必须改代码？
LLM 输出错误怎么办？
如何防止错误 Diff 应用到新版本？
为什么要有 config_hash？
为什么测试执行不能交给 LLM？
Unity telemetry 如何绑定配置版本？
Code Review Agent 如何获取上下文？
两个 Agent 为什么需要合作？
```

这些问题答得好，比现场敲十分钟代码更重要。

## 最终判断

你完全可以提前准备固定的真实代码变更，而且应该这样做。

最合适的项目演示不是：

> 现场从零开发一个功能。

而是：

> 对一个提前准备但真实存在的研发变更，现场完整执行需求理解、配置 Diff、代码审查、自动测试、Unity 运行和证据汇总。

这样既稳定，又能展示完整游戏研发 Agent 工具链。
