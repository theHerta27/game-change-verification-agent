这个调整是合理的，而且专业上不应再称为“自己做一款完整游戏”，更准确的定位是：

为游戏研发 Agent 构建一个可控、可复现、可观测的 Unity 领域测试床。
英文可以称为 Unity Game R&D Testbed 或 Playable Vertical Slice。

它需要具备真实游戏的配置、代码、测试和运行复杂度，但不承担公开发行、持续运营、完整剧情和商业美术品质。这反而更聚焦你的核心目标。

另外，“个人私下使用就完全不用担心版权”不够严谨。个人本地学习和面试演示的风险确实很低，但仍建议保留模型原始 ReadMe，不公开传播模型文件、不提交公共仓库，也不宣称模型由你制作。这样已经足够。

一、项目的最终定位
技术项目名称

Agentic Game R&D Workflow：基于 Unity 可控战斗测试床的智能游戏研发流水线

简历上可以写：

AI Agent 驱动的 Unity 游戏研发与质量保障流水线

游戏测试床名称

内部可以暂定：

幻想结界演算场

它是一段可玩的 3D 自动战斗 Roguelite 垂直切片，使用博丽灵梦模型作为本地角色表现资产。

面试时不要重点宣传“我做了一款东方游戏”，而应该说：

我构建了一个配置驱动的 Unity 自动战斗测试环境，用于验证 Agent 在游戏配置变更、代码修改、质量审查、自动化测试和运行效果评估中的能力。角色模型采用第三方资产，以减少非核心美术成本。

这样更专业，也不会把面试话题引到版权和同人内容上。

二、游戏玩法：3D 自动战斗，而不是弹幕射击
类型定义

3D 斜俯视视角、实时自动战斗、局内构筑型 Roguelite。

不是弹幕游戏，也不是传统手操动作游戏。

战斗过程中，灵梦由自动战斗 AI 控制：

自动寻找目标；
自动移动到合适距离；
自动普通攻击；
根据技能优先级自动释放技能；
躲避地面危险区域；
根据生命和敌人状态切换战斗策略。

玩家只在战斗之间进行决策：

三选一强化；
调整技能优先级；
选择恢复或输出路线；
查看当前构筑；
开始下一波战斗。

这种设计有两个优势：

仍然具有完整、直观的战斗场面；
排除了人类操作水平对测试结果的干扰，适合固定种子批量运行。
三、核心游戏循环

完整的一局控制在 6～10分钟：

选择测试场景和随机种子
→ 灵梦进入战斗场地
→ 自动完成一波战斗
→ 三选一强化
→ 下一波敌人
→ 精英战
→ 再次强化
→ Boss战
→ 生成结算和Telemetry报告

第一版规模固定为：

1个可玩角色；
1个主要战斗场景；
3类普通敌人；
1类精英敌人；
1个Boss；
6个普通波次；
1个精英波次；
1个Boss波次；
3条构筑路线；
约15个强化；
3套固定自动战斗策略；
10～20个固定测试种子。

不做大地图、剧情探索、多人游戏、装备背包和任务系统。

四、灵梦的战斗设计

虽然使用博丽灵梦模型，但玩法不做传统东方弹幕。角色定位为中距离法术战斗角色。

基础能力
普通攻击：追踪御札

灵梦向当前目标发射符札。

特征：

中距离；
轻微追踪；
稳定单体伤害；
可以通过强化变成多目标或标记体系。
技能一：阴阳玉

召唤阴阳玉攻击敌人。

初版可以采用环绕或自动冲击形式，不做满屏弹幕。

技能二：梦想结界

短时间获得护盾，并对周围敌人造成伤害或击退。

终结技能：退魔阵

在目标区域生成一个持续数秒的范围攻击区域。

五、三条构筑路线
1. 御札追踪流

特点：稳定远程输出和多目标清理。

强化示例：

御札额外追踪一个目标；
命中后施加退魔标记；
标记叠满后爆发；
击杀后弹射；
对精英和Boss提高伤害。
2. 阴阳玉流

特点：持续攻击、攻击频率和连锁效果。

强化示例：

阴阳玉数量增加；
环绕速度提升；
命中后反弹；
暴击产生范围爆炸；
多个阴阳玉同时命中触发过载。
3. 结界反击流

特点：生存、护盾和近距离反击。

强化示例：

结界吸收量提高；
护盾破裂时爆炸；
受击后缩短技能冷却；
护盾存在时获得攻击加成；
溢出治疗转化为护盾。

这三条路线正好覆盖：

直接数值调整；
Buff叠加；
条件触发；
目标筛选；
新机制扩展；
复杂代码缺陷。

非常适合 Agent 测试。

六、敌人和Boss设计
普通敌人
近战妖怪
主动接近灵梦；
普通近战攻击；
用于测试移动、目标选择和击退。
远程术士
保持距离；
发射单次远程攻击；
偶尔生成地面危险区域；
用于测试躲避和目标优先级。
重甲妖怪
移动慢；
生命和防御高；
对正面伤害有减免；
用于测试单体输出和破甲机制。
精英敌人

在普通敌人基础上增加一种特殊机制，例如：

周期性护盾；
召唤小怪；
狂暴阶段；
范围控制。
Boss

Boss设计为两个阶段，但不做复杂弹幕。

第一阶段
近战冲击；
扇形攻击；
召唤少量敌人。
第二阶段
地面危险区域；
短时间强化；
对护盾或召唤物有针对性机制。

Boss的价值不只是视觉效果，而是为 Agent 提供平衡问题：

第二阶段伤害过高；
特定流派无法通过；
某技能使用频率异常；
召唤物导致性能下降；
阶段转换存在代码缺陷。
七、自动战斗 AI

这里的“AI”不是大模型，而是确定性的游戏行为系统。专业上应称为：

Combat Policy / 战斗策略控制器

第一版用有限状态机或行为树：

AcquireTarget
→ MoveToRange
→ BasicAttack
→ EvaluateSkill
→ CastSkill
→ EvadeHazard
→ Reposition
→ Repeat

准备三种策略配置：

Aggressive
更靠近敌人；
优先输出；
较少躲避；
用于测试极限伤害。
Balanced
平衡输出和生存；
作为默认自动试玩策略。
Defensive
优先躲避；
血量较低时保留护盾；
用于验证生存型构筑。

正式评测时固定策略、固定种子和固定初始配置，避免模型修改前后测试条件不一致。

九、Agent系统结构
1. Game Change Agent

负责理解策划需求并提出变更方案。

例如输入：

Boss第二阶段对结界流压制过强。希望结界流在固定测试集中的通关率提升到40%～60%，但不能降低Boss对另外两个流派的威胁。

输出：

需求摘要；
显式和隐式约束；
受影响配置；
配置 Diff；
风险；
预期指标变化；
是否需要修改代码。
2. Code Change Agent

仅在现有运行时不支持需求时触发。

例如：

新增“护盾破裂后，将剩余护盾值转换成范围伤害”的机制。

如果当前能力清单中没有该触发器，就生成受限的 C# 候选补丁。

它不能直接修改主分支，只能在隔离工作目录产生候选 Patch。

3. Quality Review Agent

负责独立审查：

是否满足原始需求；
配置是否与运行时兼容；
C#代码是否存在生命周期、空引用、事件解绑等风险；
随机数是否破坏固定种子；
是否缺少测试；
是否引入性能问题。

原来的 DevQuality Agent 在这里演进为游戏领域的质量审查子系统，不再作为独立项目。

十、确定性研发工作流

这部分不是 Agent，而是状态机。

提交需求

→ 能力可行性判断

→ Telemetry评估

自动修订最多两次，仍然失败就转人工处理。

十二、固定演示场景

至少准备四个可复现的真实问题。

Scenario A：Boss数值过强

类型：配置问题。

Agent调整：

Boss伤害；
技能冷却；
第二阶段倍率；
结界流对应强化。

验证：

Run A与Run B通关率对比；
另外两种构筑不能被误伤得过于简单。
Scenario B：固定种子仍无法复现

类型：代码缺陷。

原因示例：

某个掉落逻辑使用系统时间初始化随机数；
某个技能直接调用未受控随机接口。

Quality Review Agent发现问题，Code Change Agent生成修复补丁。

Scenario C：护盾Buff重复订阅事件

类型：Unity生命周期问题。

表现：

Buff重复添加后事件回调没有解绑；
一次受击触发多次反击；
长时间运行后伤害异常升高。

用于验证代码审查、回归测试和Telemetry异常检测。

Scenario D：新增机制缺失

需求：

阴阳玉暴击后应该对附近敌人造成一次链式冲击。

能力清单中没有链式目标选择机制，因此从配置修改升级为代码修改流程。

最终冻结定义

这个项目最终应当被定义为：

一个使用博丽灵梦第三方角色模型进行视觉展示的3D自动战斗Roguelite测试床。游戏通过配置驱动的角色、技能、Buff、敌人、波次和战斗策略提供真实的游戏研发复杂度；三个专用LLM Agent分别负责需求与配置变更、受限代码修改和独立质量审查，确定性工作流调用Unity测试、批量自动试玩和Telemetry评估形成可回溯的研发闭环。

这个范围已经足够完整，可以正式进入《项目立项、总体设计与实施规格》的编写阶段。

Gemini给的建议怎么样？然后你也描述一下我们最终的效果应该是什么样子的？
GPT 给你规划的这个玩法非常稳，但我从实际工程开发和演示效果的角度，补充两个最关键的建议：

1. 强化数值必须“极端化”，方便 AI 看出数据变化
千万不要做那种“攻击力 +5%”的无聊强化。既然是为了测试系统，你的强化选项必须简单粗暴，比如“阴阳玉数量 +3”、“护盾血量翻倍”。
只有极端的数值，你的 AI 在收集试玩数据（Telemetry）时，才能明显看出“Run A（旧配置）”和“Run B（新配置）”的胜率有巨大差异，你在面试演示时效果才具有戏剧性和说服力。

2. 放弃复杂地形，做成“古罗马竞技场”
GPT 提到要测试“寻路”。听我的，新手用 Unity 做 3D 寻路（NavMesh）非常容易卡墙角，这会导致你的自动试玩经常因为灵梦卡住而失败。
建议： 游戏场景直接做成一个平坦的圆形大擂台，四面八方刷怪，灵梦在中间走位。把所有精力花在战斗逻辑上，不要在场景碰撞上浪费时间。

Gemini 这两条建议都很有工程价值，但第一条需要改写，第二条基本可以直接采纳。

一、关于“强化数值极端化”
有道理的部分

作为面试演示和测试场景，变化必须具有足够强的可观测性。假如只是：

攻击力 +5%
护盾值 +8%
冷却时间 -3%

即使运行20个固定种子，结果也可能被随机波动掩盖，Run A和Run B在画面上也看不出明显区别。

因此我们确实需要准备一些：

高信号测试场景（high-signal test scenarios）

例如：

阴阳玉数量从1个增加到3个；
结界护盾从100提高到180；
御札弹射目标从0增加到2；
Boss二阶段技能间隔从4秒调整到7秒；
护盾破裂新增一次明显的范围爆炸。

这类变化能同时在画面和Telemetry里体现出来。

不能走得太极端的部分

不能把整个游戏都设计成“数值翻倍”。否则会出现两个问题：

Agent只要随便把数字改大就能取得好结果；
面试官会认为这是人为制造戏剧效果，而不是可靠的平衡评测。

例如：

护盾 100 → 1000
阴阳玉 1 → 10
Boss伤害 200 → 20

虽然差异很明显，但没有分析价值。

更专业的做法是把配置分成两类。

正常游戏配置

用于表现游戏本身，数值应相对合理：

护盾：100 → 150
技能冷却：10秒 → 8秒
阴阳玉：1个 → 2个
弹射目标：0个 → 1个
诊断性测试配置

专门用于验证机制是否真正生效：

护盾：100 → 300
阴阳玉：1个 → 4个
暴击率：10% → 100%
技能冷却：10秒 → 1秒

这类配置不作为最终平衡方案，而作为自动化测试夹具，专业上可以称为：

Diagnostic Fixtures，诊断性测试夹具。

例如，我们需要确认“阴阳玉暴击触发链式冲击”是否正常，就可以在测试场景中暂时把暴击率设为100%，避免运行二十次还没有触发。

所以第一条建议应当修改成：

正式平衡调整采用可解释、受约束的中等幅度；机制验证和演示场景使用高信号诊断配置。

而不是所有强化都无脑极端化。

二、关于平坦竞技场

这条建议非常好，我基本同意。

但视觉上不一定要做成真正的“古罗马竞技场”。这只是空间结构的比喻。为了与灵梦模型和幻想题材协调，可以做成：

平坦的圆形幻想结界试炼场。

场景外观

中心是一块圆形或八角形石质场地，周围可以放：

鸟居；
石灯笼；
符纸；
结界柱；
竹林或雾气背景；
简单的远景山体；
环绕场地的发光结界。

但这些都只是装饰，不应成为复杂碰撞体。

场地结构
中央大圆形战斗区域
+
四至八个固定刷怪点
+
少量地面危险区域
+
无高低差
+
无狭窄通道
+
无可破坏障碍物

这样保留了战斗场景，又避免：

卡墙；
导航烘焙失败；
敌人堵住狭窄入口；
角色绕柱子；
自动测试因地形而不稳定。
是否还需要NavMesh

第一版甚至不一定要使用完整NavMesh。

灵梦和敌人都可以在平面上使用：

目标方向移动；
简单转向；
圆形边界约束；
基础分离力避免单位重叠；
射线检测地面危险区域。

后面为了展示Unity研发能力，可以再补一个简单NavMesh版本，但不把复杂寻路作为核心。

我们的目标不是证明你能设计复杂关卡，而是：

让每次自动战斗在相同种子和配置下稳定复现。

三、游戏最终应该看起来是什么样

最终效果不是一个灰盒测试程序，也不是完整商业游戏，而应该达到：

第一眼像一个小型完整游戏，深入看则是一个高度可测量、可修改、可回溯的研发测试床。

它应同时满足四个条件：

看得懂：战斗变化肉眼可见
玩得通：一局有开始、成长、Boss和结算
测得出：每个行为都有Telemetry
改得动：Agent能够提出并验证真实变更
1. 启动界面

打开Unity游戏后，首先看到一个简洁的测试入口：

幻想结界演算场

[开始普通演示]
[运行固定测试场景]
[选择随机种子]
[选择战斗策略]
[查看当前配置]

普通演示供人观看。

固定测试场景供Agent流水线调用，例如：

Scenario A：结界流Boss通关率过低
Scenario B：随机种子无法复现
Scenario C：护盾事件重复订阅
Scenario D：阴阳玉缺少链式冲击能力
2. 战斗画面

采用斜俯视第三人称镜头。

画面中央是使用博丽灵梦模型的角色，具备：

待机动画；
移动动画；
普攻施法；
技能施法；
受击反馈；
胜利和死亡动画。

场景为圆形幻想结界，怪物从四周进入。

灵梦会自动：

发现敌人
→ 移动到攻击距离
→ 发射御札
→ 根据冷却释放阴阳玉
→ 受到威胁时开启结界
→ 躲避Boss地面攻击
→ 重新选择目标

观众不需要操作角色，只需要观看构筑和数值如何改变战斗。

3. 战斗表现

最少应有这些清晰反馈：

御札从灵梦飞向目标；
阴阳玉在角色附近环绕或冲击敌人；
结界表现为半透明护盾；
退魔阵在地面形成法阵；
伤害数字；
暴击特殊字体或放大反馈；
敌人受击闪烁；
简短的Hit Stop或镜头震动；
Boss进入第二阶段时有明显提示。

不需要复杂画面，但每种机制必须一眼可辨认。

例如Agent把阴阳玉数量从1个改成3个，观看者应当立即看到角色周围多了两个阴阳玉，而不只是结果页面的数字发生变化。

4. HUD界面

战斗界面显示：

左上：灵梦生命、护盾
下方：技能图标和冷却
右上：当前波次、随机种子、策略
顶部：Boss生命和阶段
右侧：当前构筑与主要Buff

测试模式可以额外显示调试信息：

当前目标
当前状态
DPS
技能触发次数
随机数调用计数

普通演示模式隐藏这些调试数据，保证画面整洁。

5. 波次结束后的三选一

每一至两波结束后暂停战斗，显示三张强化卡。

例如：

御札分裂

追踪御札额外攻击1个目标，单次伤害降低10%。

双生阴阳玉

阴阳玉数量增加1个，但单个阴阳玉造成的伤害降低15%。

破碎结界

护盾破裂时，对周围敌人造成护盾最大值120%的伤害。

三张卡必须有：

名称；
图标；
简短描述；
数值；
流派标签；
稀有度或机制标签。

自动测试时，由固定策略自动选择卡牌；人工观看时，你可以手动选择。

这样既保证复现，也保留游戏感。

6. Boss战

最后一波进入Boss战。

Boss不做满屏弹幕，而使用容易观察和统计的动作：

扇形近战攻击；
直线冲锋；
地面圆形预警；
周期性召唤两只小怪；
50%生命进入第二阶段；
第二阶段缩短技能间隔。

三个流派对Boss会表现不同：

御札流持续安全输出；
阴阳玉流需要靠近，伤害高但风险大；
结界流伤害较慢，但可以反击和承受技能。

这能形成真实的平衡问题，而不是纯粹比较攻击力大小。

7. 结算页面

战斗结束后显示：

结果：通关 / 失败
随机种子：10421
构筑：结界反击流
战斗时间：7分28秒
Boss二阶段耗时：94秒
最终生命：31%
总伤害：128,430
承受伤害：8,240
护盾吸收：11,360
技能释放次数
Buff触发次数
失败或异常记录

同时将完整数据写入JSON文件，由Agent后端读取。

四、Agent控制台最终是什么效果

游戏画面只是系统的一半。另一半是浏览器中的研发控制台。

1. 提交需求

在控制台输入：

结界流在Boss第二阶段的通关率明显低于其他两个流派。希望将其在固定20个种子中的通关率提高到40%至60%，但不能让另外两条流派的通关率变化超过10个百分点。

2. Game Change Agent分析

页面显示：

需求目标
显式约束
隐式风险
受影响配置
是否需要代码变更
预期指标

Agent提出配置Diff：

dream_barrier.shield_value: 120 → 165
dream_barrier.cooldown: 11.0 → 9.5
barrier_break.damage_ratio: 0.8 → 1.1

并解释为什么没有直接降低Boss伤害：

直接降低Boss伤害会同时强化其他流派，违反交叉影响约束，因此优先调整结界流自身机制。

这句话非常适合面试展示，因为它体现了约束推理，而不是简单调大数字。

3. 确定性校验

系统自动运行：

JSON Schema校验；
配置引用检查；
数值范围检查；
运行时能力绑定检查；
版本冲突检查。

通过后等待人工点击：

批准并运行对照实验。

4. Run A和Run B

系统使用相同的：

20个固定随机种子；
相同战斗策略；
相同敌人波次；
相同游戏版本。

分别执行旧配置和新配置。

控制台展示：

指标	Run A	Run B
结界流通关率	20%	50%
平均Boss耗时	142秒	109秒
平均剩余生命	8%	24%
御札流通关率	65%	65%
阴阳玉流通关率	55%	60%

然后给出结论：

目标达成：是
约束违反：否
建议：接受配置变更

演示时可以并排播放一个失败Run和一个成功Run，让差异同时具有视觉证据和数据证据。

五、代码修改场景最终效果

第二个演示场景可以是：

同一随机种子运行结果仍不一致。

Quality Review Agent检查C# Diff后发现：

var index = new Random(DateTime.Now.Millisecond).Next(options.Count);

这绕过了中央随机数服务。

系统随后：

标记为高严重度复现性缺陷；
给出文件和代码位置；
生成一个能稳定复现问题的测试；
Code Change Agent生成候选Patch；
人工审批；
Unity编译和测试；
对相同种子重复运行；
验证关键事件序列和最终结果一致。

最终报告显示：

修复前：
同一seed运行10次，产生4种不同构筑结果

修复后：
同一seed运行10次，事件序列与结算结果完全一致

这比单纯展示LLM“发现一段坏代码”强得多，因为缺陷被真正复现、修复和验证了。

六、最终面试展示应该控制在几分钟

推荐准备一段4至6分钟的主演示。

第一部分：30秒

展示Unity游戏正常运行：

灵梦自动战斗；
三选一强化；
Boss；
结算。

让面试官先确认它不是一个假页面。

第二部分：2分钟

展示配置调整闭环：

提出需求
→ Agent分析
→ Config Diff
→ 审批
→ Run A/Run B
→ 指标改善
第三部分：2分钟

展示代码质量闭环：

固定种子失效
→ Quality Review发现问题
→ 生成测试与Patch
→ Unity验证修复
第四部分：1分钟

展示：

Run历史；
Git提交；
配置哈希；
Agent Trace；
回滚；
Benchmark指标。

最终让面试官得到的印象应该是：

这个候选人不是做了一个LLM聊天壳，而是构建了一个真实Unity运行环境，让Agent在严格约束、测试、审批和运行证据下参与游戏研发。

七、对Gemini建议的最终吸收方式

我们采用：

平坦圆形竞技场；
简化移动与寻路；
视觉上明显的机制强化；
固定种子和固定策略；
高信号演示场景。

但不采用：

所有数值都无脑翻倍；
为了展示差异而破坏真实平衡；
完全不测试移动和危险区域；
把场景做成与灵梦风格不协调的古罗马建筑。

最终场景定义可以冻结为：

一个平坦、无复杂障碍的圆形幻想结界竞技场，支持基础自动走位、目标选择和地面危险躲避；正常玩法使用合理数值，机制验证使用独立的高信号诊断配置。

这会同时兼顾开发可行性、自动测试稳定性、面试演示效果和工程可信度。
